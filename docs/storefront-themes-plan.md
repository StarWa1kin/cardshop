## 1. 已确认目标与边界

将 Admin Settings 中的“店面模板”升级为“商城主题”，提供主题 1、主题 2、主题 3，并联动用户商城。每个主题均兼容现有亮色和暗黑模式。

**最高优先级约束：用户商城端保留原有字段、接口契约、业务逻辑与交易流程，只调整 UI。新增或调整的主题专用字段由本计划单独定义。**

### 1.1 允许的变更

- 页面布局、导航呈现、颜色、字体、间距、圆角、边框、阴影、图标和装饰资源。
- 组件展示结构、响应式布局、无障碍属性、动效与视觉反馈。
- 纯 UI 状态，例如菜单展开、弹层开关、焦点、悬停及主题预览状态。
- 主题注册、主题专用配置、主题资源加载及相关测试。
- Admin 主题设置界面、主题配置保存与公开配置中的主题字段。

### 1.2 保持原样的内容

- 原有商品、分类、SKU、库存、价格、币种、折扣、批发价和限购字段，包括名称、类型、含义及空值处理。
- 商品查询条件、搜索匹配、排序规则、分页语义和既有分类筛选行为。
- 登录注册、访客购买、验证码、权限判定、购物车存储及商品合并规则。
- SKU 选择校验、购买数量限制、手工交付表单、优惠券、订单创建、支付渠道、手续费与支付金额计算。
- 订单查询、订单状态、自动/手工/上游交付、退款、充值、分销与推广归因逻辑。
- 非主题接口的路径、请求字段、响应字段、校验顺序和既有错误语义。
- 原有路由路径、业务 query 参数、重定向规则、SEO 与后台已有内容配置的作用。
- 原有 `template_mode` 的 `card/list` 值及其含义；原有 `dujiao_theme`、`cart_items` 等存储格式。

**不以 UI 重构为理由顺带重写 store、API 层、计算公式或交易状态机。** 如某个设计交互依赖新增业务能力，该交互留待后续单独评估，首版保留原入口与原流程。

## 3. 三个独立维度

| 维度 | 值 | 决策方 | 行为 |
| --- | --- | --- | --- |
| 商城主题 | `theme-1/theme-2/theme-3` | 管理员 | 决定展示布局与风格 |
| 明暗模式 | `light/dark` | 访客，沿用现有偏好 | 决定主题的亮/暗配色 |
| 商品展示方式 | 原有 `card/list` | 管理员 | 沿用现有业务与展示语义 |

- 切换主题不覆盖用户明暗偏好，不清空购物车，不影响登录态。
- 沿用当前首次访问按系统偏好初始化的机制；首版不新增强制配色或跟随系统实时变化等设置。
- Admin 自身的明暗模式独立于商城主题。
- 分销商城首版继承主站主题；分销管理控制台保留原有视觉边界，不新增分销站独立选主题能力。

## 4. 主题字段与存储设计

### 4.1 采用独立设置项，降低对旧字段的影响

在现有设置存储机制中新增独立 key：`storefront_theme_config`。首版仅包含一个写入字段：

```json
{
  "key": "storefront_theme_config",
  "value": {
    "theme_id": "theme-3"
  }
}
```

- `theme_id` 仅接受三个稳定 ID，显式提交空值或未知值时返回配置校验错误，保留原保存值。
- 不新增业务数据表；复用已有设置存储、后台鉴权及更新机制。
- 在设置注册机制登记新 key 与公开配置缓存失效副作用，并在写入边界增加主题专用校验。
- 新主题单独保存，不混入原 `site_config` 的全量表单提交，避免旧后台保存其他设置时丢失新主题配置。
- 原 `site_config.storefront_template` 保留原字段和值，不重命名、不删除、不双写伪装主题 3。
- 相比讨论阶段“把新字段直接加入 site_config”的初步想法，此处收敛为独立设置项，以更严格落实保留旧字段与旧保存流程的要求。

### 4.2 商城公开配置

在现有 `/public/config` 响应中新增主题专用字段 `storefront_theme`，其值为解析后的有效主题 ID。原有字段原样保留。

正式主题解析优先级：

1. 新设置中合法的 `theme_id`。
2. 旧 `storefront_template = vault` → `theme-2`。
3. 旧 `storefront_template = classic` → `theme-1`。
4. 新旧设置均缺失或旧值未知 → `theme-1`。

异常存量新值按缺失处理，并记录诊断信息；正常写入阶段禁止保存异常值。前端面对未知主题值时同样回退到可用主题，避免白屏。

**读取旧配置时先执行兼容映射，再填默认值。** 首次部署不写入默认 `theme-1`，避免覆盖原先启用 `vault` 的站点。

### 4.3 兼容与发布顺序

- 新前端遇到旧后端：根据 `storefront_template` 映射，继续显示旧主题。
- 旧前端遇到新后端：忽略新增字段，继续显示原 `storefront_template` 指定的旧主题；主题 3 只面向新前端。
- 后端先支持主题配置与公开字段，再部署新商城和新后台，最后启用主题 3。
- 一旦显式保存新主题，以新设置为准；旧后台再修改旧模板字段不覆盖新主题。
- 新主题保存成功后复用公开配置缓存失效能力，覆盖继承主站主题的分销域名缓存。
- 不增加实时推送、轮询或全站强制刷新。保存后，新打开或刷新商城生效；正在结算中的页面保持当前会话。

## 5. Admin Settings 设计

- 将“店面模板”展示文案升级为“商城主题”，同步简体、繁体与英文文案。
- 抽出主题设置面板，展示三张主题卡片、主题说明、亮暗缩略图、预览入口、当前主题和待保存状态。
- 选中卡片只修改本地待保存值，点击“应用主题”才提交独立主题设置。
- 保存失败保留待保存状态并提示；只有服务器确认成功才更新“当前主题”。
- 商品“卡片/列表”继续使用原字段、原保存入口；UI 明确区分“主题应用”和“商品展示设置”，避免部分保存被误报为全部成功。
- 主题保存不触发其他设置提交；保存其他设置也不重置当前主题。
- 预览的亮暗切换只影响预览区域，不改后台主题或访客正式偏好。

## 6. 前端主题架构

### 6.1 注册表与职责

将现有双模板解析升级为三主题注册，集中声明主题 ID、文案 key、布局加载器、页面展示加载器和预览资源。使用静态白名单，不按用户输入拼接任意导入路径。

- 主题 1 继续引用现有 views，不搬迁整套旧页面。
- 主题 2 继续引用现有 vault，不复制其业务代码为第三份。
- 主题 3 新增布局、主题变量、商品展示和页面展示组件。
- 共享页面优先继续挂载现有业务组件，只替换展示外壳、插槽或纯展示组件。
- 若页面业务与模板高度耦合，先识别可复用的展示边界；首版宁可复用该页面并主题化样式，也不复制或改写其业务脚本。
- 不因改主题批量重构 composable、store 或 API；主题 3 展示组件通过既有 props/emits/事件回调消费原能力。

### 6.2 配置加载与页面解析

- 继续在路由首次选择页面前加载公开配置，沿用当前守卫中的业务检查。
- 正式主题在本次页面加载期间保持一致；不只更新外壳而保留已解析的旧主题页面。
- 首版通过完整导航进入不同主题预览，正式切换通过刷新生效，不依赖给 RouterView 加 key 来解决路由懒加载缓存。
- 缺少主题专属页时，使用经过验证的现有页面与主题变量，不显示空白页；发布前对全部页面做覆盖检查。
- 主题 3 的脚本和主视觉按需加载，不让主题 1/2 用户预先下载整套新资源。
- 配置加载中使用中性加载态，避免先渲染主题 1 再明显跳变到主题 3。

### 6.3 主题变量与浮层

- 复用 `--ui-*` 语义变量、现有 Tailwind 映射和根节点 `.dark`，不引入第二套明暗状态。
- 用 `data-storefront-theme` 标识当前商城展示主题；为主题 3 的亮暗状态分别定义变量。
- 将根级配色变量覆盖到浮层继承范围，涵盖 Toast、确认框、公告弹窗、下拉菜单和其他 Teleport 内容。
- 字体、布局和卡片结构规则限定在商城主题作用域；进入分销控制台时解除商城主题覆盖，退出时恢复。
- 统一管理作用域切换与清理，避免旧 vault 的 body 类与新主题标识残留叠加。
- 价格、库存、警告、错误、禁用与焦点状态都使用语义颜色；科技主色不替代业务状态色。

## 7. 主题预览隔离

- 使用新主题专用 query 参数 `theme_preview=theme-3` 与可选的 `theme_preview_mode=dark`；它们只选择展示，不改变接口数据或访问权限。
- 仅当前显式预览 URL 生效；显示“主题预览”和“退出预览”入口。
- 不将主题预览写入 localStorage 或跨标签页持久状态。站内预览链接如需连续浏览，仅携带主题专用参数，保留原业务 query。
- 退出预览时仅移除主题专用参数，通过完整导航回到正式配置；不清理其他 URL 参数和用户数据。
- 新机制上线时仅清理旧 `dj-storefront-template` 覆盖键，停止旧 `?template=` 的持久覆盖行为；保留其他存储键。
- 预览明暗值只控制本次预览显示，不回写 `dujiao_theme`；退出后恢复真实用户偏好。
- 预览不提交主题配置，也不是订单沙箱：真实站点预览里的交易仍执行原业务规则。后台静态缩略图用于无交易风险的视觉浏览。

## 8. 主题 3 UI 与交互细则

### 8.1 视觉规范

- 暗色：深石墨页面、略提亮的卡片层、克制的青色边缘高光。
- 亮色：冷白页面、淡灰蓝分层、深色文字与更深的青色链接，保证可读性。
- 青色高亮按钮优先深色文字，避免亮青底白字对比不足。
- 圆角以 12–16 px 为主，布局采用 8 px 间距节奏，细边框与轻阴影，不大面积模糊。
- 仅主视觉和商品装饰资源使用玻璃/金属质感，正文与价格保持清楚锐利。
- 以现有字体与图标能力优先实现，避免新增大型 UI/动画框架。
- 主视觉是独立装饰资源，真实商品图优先；缺图时使用统一类别占位，避免替换真实商品含义。

### 8.2 交互约束

| 交互 | 视觉表现 | 业务边界 |
| --- | --- | --- |
| 商品 hover / focus | 轻微上浮、青色边框、操作入口显现 | 不加载或修改额外业务状态；键盘同样可达 |
| 分类与搜索 | 选中态、清晰输入、加载反馈 | 保持原查询、排序、分页及搜索规则 |
| 快捷选规格 | 桌面弹层、手机底部面板 | 仅在完整复用既有购买控件与校验时启用，否则跳转原详情页 |
| 加入购物车 | 原操作成功后显示 Toast 和角标变化 | 沿用原 addItem 与校验，不乐观伪报成功、不绕过规格选择 |
| 购物车入口 | 角标与短促强调动画 | 不改变商品合并、计数或持久化算法 |
| 明暗切换 | 背景和文字短过渡 | 使用原偏好，保留业务状态 |
| 请求中/失败 | 既有 loading/error 对应的 UI | 不新增重试策略，不改变请求时机和错误处理业务语义 |

- 快捷选购实施前检查实际 SKU、数量限制、手工表单、购买方式与身份限制；任一条件缺少可复用能力时，显示“查看详情”。
- 单纯调用 cart store 不等于完整复用购买校验；禁止以此省略现有详情页约束。
- 库存和价格使用原格式化、隐藏策略与真实字段；不因为设计稿需要而补造“有库存”或折扣标签。
- 动效建议 150–220 ms，以 opacity/transform 为主；尊重 `prefers-reduced-motion`。
- 弹层支持 Esc 关闭、焦点约束与关闭后焦点恢复；交互不依赖 hover 才可发现。
- 搜索快捷键仅属于 UI 聚焦能力；如实现，必须避开输入框、编辑器及输入法组合状态。

### 8.3 响应式与完整状态

- 桌面：主视觉双栏、按可用宽度展示 3–4 列商品，不把概念图比例硬编码为生产布局。
- 平板：2–3 列、紧凑导航；手机：单列主视觉与 1–2 列商品，列表模式保留原行为。
- 测试 375、768、1440 px 代表宽度，并覆盖长商品名、多规格、长价格及多语言。
- 覆盖 loading、空列表、搜索无结果、售罄、库存隐藏、禁用、表单错误、图片失败与登录/未登录状态。
- 禁止通过纯 CSS 隐藏仍然必填的业务表单，或将关键支付信息挤出可见区域。
